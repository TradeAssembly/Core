# Binary updates: implementation and rollout

Status: the distribution library and `tradeassembly-distribution update-plan`
implement offline signature verification and update eligibility. On Unix,
`update_cache` adds bounded HTTPS artifact downloading, private atomic caching,
exclusive locking and durable trust/replay receipts. There is no timer, native
activation wiring, production signing key, or published binary feed yet. Existing installations are unchanged. This is not release proof.

## Installation profiles

The installation descriptor uses a closed `profile` object. Customer installs
use `{"mode":"stable"}`. A chosen development version uses
`{"mode":"development","version":"0.2.0"}`; an explicitly pinned installation
uses `{"mode":"pinned","version":"0.2.0"}`. Both require that exact installed
version and return `disabled` without inspecting metadata. Switching profiles is
an explicit future installer operation, never an environment-variable override
of a customer's running process. Development and stable installations must have
distinct roots, application identities and service registrations.

The descriptor also names `product` (`core-bundle` or `studio-local`), `version`,
`target`, `state_compatibility`, `accepted_sequence`, `archive_sha256`, and
`bundle_manifest_sha256`. The CLI currently reads this descriptor from a file;
it does not mint trusted installed-state receipts or persist update freshness.

## Authenticated metadata

The closed JSON envelope contains `payload` and `signature` in standard base64.
Payload bytes are JSON for `updates::BinaryRelease`. Ed25519 signs exactly
`b"tradeassembly.binary-update.v1\0" || payload_bytes`. The verifier uses a public
key from trusted release configuration, never a key in the downloaded feed.
Metadata expires within seven days, binds product, stable channel, target, exact
version, increasing sequence, state compatibility, immutable GitHub asset URL,
archive and bundle-manifest SHA-256, and a map of constituent SHA-256 identities.
No Hub subscription or hosted runtime dependency is required by this public code.

`update-plan --installation FILE --manifest FILE --public-key BASE64` returns
`disabled`, `current`, or `stage`. `stage` is an instruction to the future
download controller, not evidence that any download or filesystem staging happened.
Inputs are bounded at 64 KiB. Errors leave the installation untouched. Stable
metadata cannot select prereleases, downgrade, cross-update products/platforms,
change bytes at the current version, or cross a state migration boundary.

## Authenticated download cache

`UpdateCache::enroll` explicitly binds an empty private cache to a canonical
installation root, product, platform, profile and public key. `open` rejects any
trust change. Artifact downloads use HTTPS with verified TLS, no credentials or
proxy inheritance, an explicit GitHub release redirect allowlist, finite connect/
total timeouts, identity content encoding and a 512 MiB streaming bound. SHA-256
is checked before the cache file and signed receipt are atomically published and
synced. Failed downloads preserve a durable highest-seen metadata identity; only
that exact envelope can retry the sequence. Verified cached bytes can retry offline.

`with_ready` holds the cache lock, rechecks metadata freshness, exact envelope and
archive hashes, and passes an authenticated archive handle to the owning installer.
It does not itself execute or unpack the archive. The combined customer installer
in the private coordinator owns Core/Relay transitions; this public library must
not independently replace Core beneath that paired delivery. Windows cache ACLs
and native activation wiring remain unimplemented and are not implied by Unix tests.

## Next integration gates

1. Bind profiles and trusted public keys into authenticated install receipts.
   Default developer builds to development; customer builds must carry the updater.
   Never infer profile from PATH, checkout names, or arbitrary feed parameters.
2. Obtain approval for production binary-feed signing key custody if no suitable
   existing key is approved. Apple Developer ID code signing is separate from
   Ed25519 update metadata. No production key has been generated by this change.
3. Implement finite HTTPS checks/downloads with redirect allowlists, byte limits,
   signature and digest validation, private staging, cancellation/backoff, and
   durable highest-seen sequence under a lock. Bind every constituent in the
   verified bundle to the authenticated manifest; never float a pinned plugin,
   Warden, Node, sandbox or companion independently. Distribute private products
   through the existing authorized channel without placing them in public Core.
4. Connect staged activation to the existing installer transaction/recovery and
   stopped-state/process-lock checks. Do not stop active trading automatically.
   Automatic checks/downloads may continue during work; replacement and restart
   wait for a supported safe stopped state and visible restart policy. Preserve
   identity, credentials, data, config, and the last working distribution.
5. Add Studio native integration and platform qualification against the same
   coordinated constituent set. Hosted Relay/Hub/web updates use owning deployment
   and rollback processes; they must not run binary self-updaters. Standalone
   CLI/service installs need an explicit owned updater service/timer with the same
   policy and a stop/restart contract. Package-manager ownership must not race it.
6. Run old-to-new, failure/offline, interrupted transaction, rollback, active-rig
   refusal, exact pin, dev isolation and installed native acceptance on real
   qualified artifacts. Full owning gates and release approval remain required.

## Migration and retirement

Old versions without an updater require a one-time normally installable bridge
installer in the existing installation root. Merely removing their downloads
cannot update existing customers. Keep immutable rollback bytes and offer the
bridge at legacy download entrypoints with clear instructions; after proving the
bridge, switch customer-facing links to updater-capable releases reversibly.
Do not retag old releases or rewrite their archive contents.

Retirement requires a qualified replacement, old-to-new preservation proof,
working upgrade feed and demo-owner confirmation that the exact recorded build
has been retained and recording completed. Inventory Bender and Zoidberg before
cleanup; no active processes, developer checkouts, pinned profiles or customer
state are deletion targets. First unlink obsolete launchers/service registrations
only after verifying replacement ownership; quarantine old executable bundles with
hashes and a restoration manifest. Permanent deletion needs exact action-time
approval. No downloads or installs were removed by this change.
